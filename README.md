# CaOS — Cafeore Operating System

コーヒー提供現場で、6人のドリッパー（抽出担当者）へ注文を割り当て、進行状況を一画面で把握するためのタッチ操作向けUIモックです。iPadの横画面を想定し、管制盤を常に表示したまま操作できます。

これまでに決定した画面・操作・業務ルールの詳細は、[画面設計・操作要件](./DESIGN_REQUIREMENTS.md)を参照してください。

## プレビュー

[CaOSをGitHub Pagesで開く](https://cafeore-tkb.github.io/digital-master-sheet-pages/)

`main` のソースをビルドし、`npm run publish:pages` で公開します。

## 画面

- **A**: NOW線を基準に、6人のレーンと時間軸で進行・待機カードを確認する管制盤
- **B**: 現在・次の抽出と未割当注文を、よりコンパクトに確認する比較案
- **C**: 担当者ごとのドリッパー（H1/H2・I1/I2）と残り時間を並べ、現在の抽出と次に空く担当者を確認する比較案
- **D**: 紙のマスターシートを画面上に再現する案。6人を列、注文番号を行とした表に、右の注文カードを選んで枠をタップするか、列へドラッグして割り振ります（[cafeore-pos#699](https://github.com/cafeore-tkb/cafeore-pos/pull/699) のコンセプトを移植）
- 最上段のヘッダーまたはサイドバーからA/B/C/Dを切り替えます。
- 補助情報は右側パネルに表示し、管制盤全体を隠しません。

### 管制盤A〜Dの比較

4案とも同じ注文データ・業務ルール（オーダー番号順、指名、最大2杯、`次へ` で完了、緊急の入れ直し）を共有し、違うのは見せ方と割当の操作だけです。

| | A：タイムライン | B：コンパクト | C：ドリッパー行 | D：マスターシート |
|---|---|---|---|---|
| 担当者の並び | 6レーン（横軸＝時刻） | 6列 | 6行（左半分） | 6列（表の列） |
| 待機列の見え方 | 時間軸上のカード位置で全件 | 現在＋次の1件のみ | 現在＋待機を横並びで全件 | 注文番号の行に全件（全注文番号に行があり、列を上から読むと担当者の順番） |
| 時間の情報 | NOW線と時刻目盛り、開始・終了予定、次に空く上位3人 | 現在の残り時間、次に空く上位3人 | 現在の残り時間、次に空く上位3人 | 列見出しの残り時間のみ |
| 完了済みの表示 | NOW線の左（過去90秒）に薄く | なし | なし | すべて元の行に薄く残す（行は動かさず下へ積む） |
| 未割当の置き場所 | 下段の横帯（先頭12件） | 下段のグリッド（10注文） | 右半分の縦リスト（全件） | 右の注文カード（全件） |
| 未割当の単位 | 抽出カード | 注文（分割カードをまとめる） | 抽出カード | 注文（割当済み分も薄く表示） |
| 割当操作 | タップで1〜6ボタン／なぞり／ドラッグ | タップで1〜6ボタン | タップで1〜6ボタン／なぞり／ドラッグ | カードを選んで表の「ここに配置」をタップ／列へドラッグ |
| 割当後の移動・戻し | レーン間ドラッグ、タップで1〜6／×で戻す | 詳細モーダル | 詳細モーダル | 列間ドラッグ、右の注文内容へドラッグで戻す、詳細モーダル |
| 1杯カードの統合 | あり | なし | なし | あり（統合した2注文の行を、間の行ごと大きな枠で囲む） |
| 主な実装 | `DispatchBoard` + `UnassignedOrdersPanel` | `ControlViewB` | `ControlViewC` + `DripperOrderCard` | `ControlViewD` |

- **A：タイムライン**　時間の流れを最も正確に表す基準案です。待ち時間の偏りや「誰がいつ空くか」が位置で読めて、ドラッグで再配置できます。代わりに情報量が多く、横スクロールやカードの小ささで一覧性が落ちやすくなります。
- **B：コンパクト**　「今何を淹れているか・次は何か」に絞った案です。1人あたりの表示が大きく遠目でも読みやすい反面、3件目以降の待機が見えず、ドラッグにも対応していません。注文単位でまとめるので、分割注文の行き先を追いやすいです。
- **C：ドリッパー行**　担当者を行にして、現在の抽出と待機列を横に並べる案です。器具ラベル（H1/H2・I1/I2、1番と6番の限定）を担当者ごとに表示し、未割当を右半分に全件並べます。待機列が長くなると行内の横スクロールになります。
- **D：マスターシート**　紙運用をそのまま置き換える案です。行＝注文番号（未割当や抽出のない番号も詰めずに1行ずつ）なので「どの注文を誰が淹れるか」と注文ごとの杯数が表で揃い、紙に慣れた人が移行しやすいです。淹れ終わっても行は動かず、新しい注文は下へ積まれていきます。割当は2回のタップか列へのドラッグで済み、割当後もドラッグで列を移したり未割当に戻したりできます。統合した1杯同士は、2注文の行とその間の行をまとめて囲む大きな枠で表示します。注文が増えると表が縦に伸びてスクロールが要ります（開いたときは淹れ終わっていない最初の注文付近を表示）。

## 主な挙動

- cafeore-pos で受けた注文は、抽出カードになって未割当に並びます。割当や抽出の状態は DB に保存され、どの iPad で開いても同じ盤面になります。
- 未割当注文と各ドリッパーの待機列は、指名注文を含めて原則オーダー番号順です。
- 指名注文は指定されたドリッパーにのみ割り当てられます。
- 1回の抽出は最大2杯です。3杯以上の注文は2杯以下のカードへ自動分割します。
- 同じメニューの1杯カード同士だけ、利用者の判断で2杯の同時抽出へ統合できます。
- `次へ` を押すまで現在の抽出は継続中です。押した時点を基準に、後続カードすべての開始位置を再計算します。
- 抽出前のカードは、別のドリッパーへの移動または未割当に戻す操作だけができます。
- 通常のホットは無色、氷・牛乳・指名・`★SP` は識別色で表示します。
- `1/1・計○杯` は省略し、分割された注文だけ `1/3・計4杯` のように全体量を表示します。
- 抽出中・完了済みカードから緊急の入れ直しを開始でき、中断／継続、杯数、担当者、差し込み位置を利用者が選べます。
- アイスミルクは売上分析には残しつつ、ドリップ管制の未割当・タイムラインから除外します。

## cafeore-pos 連携

CaOS は cafeore-pos と同じ Postgres（Supabase）の `caos` スキーマを、supabase-js で直接読み書きします。間に CaOS 専用のサーバーやプロキシは置きません。

```
[CaOS の画面（iPad 数台）]
   │ supabase-js
   ▼
[Supabase]
 ・ログイン = Supabase Auth（Google）。書き込めるのは caos.staff に登録したスタッフだけ
 ・権限     = RLS。スタッフは caos.drips を読めるだけで、書き込みは RPC に限る
 ・同期     = Realtime。変わったカードの行だけが届く
 ・操作     = Postgres 関数（caos.assign / unassign / next / merge / rebrew / restore）
 └ 中身は POS と同じ Postgres（caos スキーマ。POS の表は public スキーマ）
```

- 抽出カード（1 回のドリップ、最大 2 杯）を `caos.drips` に 1 枚 1 行で持ちます。保存するのは担当・状態・開始/終了時刻などの事実だけで、待機カードの予定時刻は画面で計算します。
- 注文が入ると、`public.order_menus` のトリガーがカードを作ります（2 杯ずつ分割。アイスミルクとグッズは除く）。注文を編集・削除すると、未割当のカードだけを作り直します。
- `次へ` で注文のカードが全部終わると、その注文に `ready_at` を付けます（POS の準備完了）。逆に POS で準備完了・提供済みにすると、その注文のカードを抽出終了にし、抽出中だったドリッパーは次のカードを始めます。CaOS が 1 台も開いていなくても DB の中で動きます。
- 割当・移動・未割当へ戻す・統合・入れ直し・`次へ`・`1つ戻す` は、どれも RPC を 1 回呼ぶだけです。サーバー側で順に処理するので、複数の iPad で同時に操作しても上書きし合いません。`1つ戻す` は、ほかの端末がその後にカードを動かしていたら断ります。
- 実データテスト中は DB を使わず、テストの注文だけで手元の盤面を動かします。終了後の実績表示中も DB は使わず、リセットすると DB の盤面に戻ります。
- ヘッダーの DB アイコンが状態を表します。緑は接続済み、黄は接続中・再接続中、赤の「未登録」はログインしたアカウントが `caos.staff` に無いとき、灰色は実データテスト中か Supabase 未設定です。未ログインのときは「ログイン」ボタンになります。
- メニュー名から豆を判定します（優勝ブレンド→チャンプ、俺ブレ、ケニア、タンザニア、ブラジル、アイスコーヒー→氷、アイスオレ→牛、それ以外のホット→★SP）。
- POS の指名は、`1`〜`6` の番号か現在のドリッパー名に一致したときだけその担当者に固定し、一致しないときはカードに「（指名:名前）」と表示します。
- POS の画面へは、cafeore-pos の API が DB の `orders_changed` 通知を受けて配り直します（cafeore-pos の `api/sql/2026-10_orders_notify.sql`）。CaOS が付けた `ready_at` もこれで POS に届きます。

### Supabase のセットアップ

本番の Supabase プロジェクトで、管理者が 1 度だけ行います。

1. `supabase/migrations/` の SQL を順に流します（SQL Editor か `supabase db push`）。`public` スキーマの表から `anon` / `authenticated` の権限を外すので、POS の API（Go）は今までどおりオーナーのロールで接続していることを確かめてから流してください。
2. Data API の Exposed schemas に `caos` を足し、`public` は外します（POS の表を匿名キーから見えなくするため）。
3. Authentication の Providers で Google を有効にし、Redirect URLs に公開版（`https://cafeore-tkb.github.io/digital-master-sheet-pages/`）と開発用（`http://localhost:3000/`）を足します。
4. 使うスタッフの Google アカウントを登録します。

   ```sql
   insert into caos.staff (email) values ('someone@example.com');
   ```

5. CaOS のビルドに Project URL と anon key を渡します（`.env.local` か、GitHub Actions の Variables の `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`）。anon key は公開してよい鍵です。

マイグレーションは、共有 DB のスキーマ用リポジトリができたらそちらへ移します。

### SQL のテスト

ローカルの Postgres に使い捨てのデータベースを作り、マイグレーションを流して運用の流れ（注文 → カード作成 → 割当 → 次へ → 準備完了、POS 側の準備完了、統合、入れ直し、1つ戻す、権限）を確かめます。

```bash
TEST_DATABASE_URL=postgres://postgres@127.0.0.1:5432/postgres bash scripts/test-supabase.sh
```

## 実データ・テストプレイ

- ヘッダーの「実データテスト」から、2025年の実注文を使ったテストプレイを開始できます。
- 開始前に時間帯と30分／1時間を選択します。ヘッダーの `1x / 2x / 5x / 10x` に合わせて、時計・タイムライン・注文到着・抽出時間が実時間基準で一緒に進みます。
- 「終了・実績」を押すと、売上、商品構成、ピーク、提供時間、担当量、分割注文の仕上がりΔを表示します。
- 指定された `2025/data/day1.json` は空ファイルだったため、同じリポジトリにあるダミー除去済み `2025/data/day12.json` を軽量化して同梱しています。
- 実績データはビルド時に遅延読込用JavaScriptへ内包し、公開サイトに生JSONのURLを作りません。
- データ出典: [cafeore-tkb/sohosai-analysis](https://github.com/cafeore-tkb/sohosai-analysis/tree/main/2025/data)

## 公開構成

- ソースと実績データはPrivateの `cafeore-tkb/CaOS` で管理します。
- Private側のActionsはPages用ビルドを検証し、成果物を保存します。
- `npm run publish:pages` を実行すると、ビルド済みの `site/` だけをPublicの `cafeore-tkb/digital-master-sheet-pages` へ送り、公開側のPagesワークフローが更新します。
- `main` の成果物を `site/` 直下に配置します。
- 公開成果物には生JSONを置かず、実績データはハッシュ付きの遅延読込JavaScriptに内包します。

## タッチ操作

- 未割当カードをタップすると、カードを隠さず上下に1〜6の割当ボタンが開きます。
- 指を離さず割当先へなぞる操作と、レーンへのドラッグ操作に対応しています。
- 枠外をタップすると選択状態を解除します。
- タイムライン上の未開始カードも、同じ操作感で割当先を変更できます。
- Dでは右の注文カードを担当者の列へドラッグすると、その担当者に割り当てます。表の未開始カードは別の列へドラッグして移すか、右の注文内容へドラッグして未割当に戻せます。縦の動きはスクロールに使うため、横へ引き出すと掴めます（右で選択中のカードはどの方向にもドラッグできます）。
- Dで1杯カードを選ぶと、統合できる同じメニューの1杯カードに「統合する」が出ます。統合後のカードは前の注文番号の欄に移るため、自動で選択してその位置までスクロールします。

## 開発

Node.js 22を推奨します。

```bash
npm install
npm run dev
```

開発サーバーは `http://localhost:3000` で起動します。DB につなぐには `.env.local` に Supabase の接続先を書きます（`.env.example` を参照）。本番の DB を指すと実際の注文を操作することになるので、開発用の Supabase プロジェクトを使ってください。

```bash
npm run lint
npm run build
```

本番ビルドは `dist/` に生成され、公開時のベースパスは `/digital-master-sheet-pages/` です。
